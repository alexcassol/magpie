# Order inbox

A supplier drops a CSV into Dropbox. A worker imports the orders, writes a
receipt, and archives the file. If Dropbox becomes unavailable after the orders
have been saved, the next run finishes the report and archive without importing
those orders again.

This is a small integration service: Dropbox handles delivery, while a local
journal holds the business records and pending work. The same pattern fits
supplier feeds, accounting imports, and documents awaiting review.

## Run offline

From this repository:

```sh
cd examples/order_inbox
mix deps.get
mix test
MIX_ENV=test mix run demo.exs
```

The demo uses `Req.Test` and a temporary journal. It makes no network requests
and needs no Dropbox account. It imports two orders, simulates an archive
failure, restarts the journal, and confirms that the order count stays at two.

## Run against Dropbox

Use a Dropbox app with `files.metadata.read`, `files.content.read`, and
`files.content.write`. For an App Folder app, the paths below are relative to
that app's folder. See the [OAuth guide](../../guides/oauth.md) for setup.

Set a short-lived access token in your shell:

```sh
export DROPBOX_ACCESS_TOKEN='your-access-token'
mix inbox.run
```

For a long-running worker, set `DROPBOX_REFRESH_TOKEN`, `DROPBOX_APP_KEY`, and
`DROPBOX_APP_SECRET` instead. The refresh token takes precedence when present.

The first run creates `/MagpieOrders` and its subfolders. Copy
[`fixtures/orders.csv`](fixtures/orders.csv) into `/MagpieOrders/Incoming` using
Dropbox, then run:

```sh
mix inbox.run --root /MagpieOrders --state var/orders.json
```

Or poll every 30 seconds:

```sh
mix inbox.run --root /MagpieOrders --state var/orders.json --watch
```

All paths and the journal location can be changed with those options. Use a
dedicated top-level Dropbox folder; do not point this at an existing document
collection. Stop the watcher before running a one-shot import with the same
journal.

## Follow one import

```text
Incoming/orders.csv
    -> Processing/<receipt-key>.csv
    -> parse and validate
    -> save orders + receipt in one journal write
    -> Reports/<receipt-key>.json
    -> Processed/<receipt-key>.csv  (or Rejected/)
    -> mark receipt delivered
```

The receipt key hashes the Dropbox file ID and revision. Moving a file into
`Processing` claims that particular file; a supplier can then upload a new
`Incoming/orders.csv` without replacing the file being imported. Downloads use
`rev:...` so they read the revision being recorded.

The CSV format is one order per row:

```csv
order_id,sku,quantity
ORDER-1001,NOTEBOOK-A5,12
ORDER-1002,"MUG, BLUE",3
```

The parser accepts quoted commas. It requires the exact header, at least one
row, nonempty IDs and SKUs of at most 100 bytes, and quantities from 1 to 10000.
Files over 2 MiB are rejected. One invalid row rejects the whole file. An
`order_id` already imported from another receipt also rejects the whole file;
this sample does not treat a changed quantity as an order update.

Try [`fixtures/invalid.csv`](fixtures/invalid.csv) to see a rejection report.
Orders and receipts are readable in `var/orders.json`. Do not edit this file
while the worker is running.

## Recovery behavior

| Interruption | Next run |
| --- | --- |
| After moving to `Processing`, before saving | Finds the claimed file and imports it. |
| After saving, before writing the report | Rewrites the same report and retries the archive. |
| Archive succeeded but its response was lost | Looks up the file ID, sees the final path, and completes the receipt. |
| Claimed file was edited | Leaves the receipt pending with `:revision_changed`. |
| CSV contains an existing order ID | Writes a rejection report; stores none of its rows. |

`Processing`, `Processed`, and `Rejected` belong to the worker. Keep human
edits and other processes out of those folders. The revision check before a
move is not a conditional move; it cannot prevent an edit racing with that
request. The offline tests exercise recovery and check the actual Magpie
request paths and payloads.

## Read and adapt the code

- [`lib/order_inbox.ex`](lib/order_inbox.ex): claim, download, report, archive,
  and resume pending receipts.
- [`lib/order_inbox/journal.ex`](lib/order_inbox/journal.ex): orders and receipts
  saved together, with a temporary file and rename.
- [`lib/order_inbox/csv.ex`](lib/order_inbox/csv.ex): validation independent of I/O.
- [`lib/order_inbox/worker.ex`](lib/order_inbox/worker.ex): polling worker that can
  run under your application's supervisor.
- [`test/order_inbox_test.exs`](test/order_inbox_test.exs): recovery, rejection,
  duplicate IDs, revision changes, and journal write failure.

The journal is deliberately small: it rewrites the whole JSON document and
supports one process on one machine. Preserve it across runs; deleting it
loses the import history. It demonstrates process-restart recovery, not a
distributed lock or a power-loss durability guarantee.

For a real order system, replace the journal with a database transaction that
inserts the orders and receipt, protected by unique constraints on order ID
and receipt key. Keep report/archive work in an outbox. If importing triggers
a payment, email, or ERP call, that downstream operation also needs its own
idempotency key. A Dropbox receipt alone cannot make those effects atomic.
